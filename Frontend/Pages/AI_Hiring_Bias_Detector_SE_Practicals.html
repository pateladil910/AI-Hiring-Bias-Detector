Practical 1: Preparing Software Requirements Specifications

Objectives

  • Identify ambiguities, inconsistencies, and incompleteness from a requirements specification
  • Identify and state functional requirements
  • Identify and state non-functional requirements

1.1 Requirements

Sommerville defines "requirement" as a specification of what should be implemented. Requirements specify how the target system should behave. It specifies what to do, but not how to do. Requirements engineering refers to the process of understanding what a customer expects from the system to be developed, and to document them in a standard and easily readable and understandable format. This documentation will serve as reference for the subsequent design, implementation, and verification of the system.

It is necessary and important that before we start planning, design, and implementation of the software system for our client, we are clear about its requirements. If we don't have a clear vision of what is to be developed and what all features are expected, there would be serious problems and customer dissatisfaction as well.

1.2 Characteristics of Requirements

Requirements gathered for any new system to be developed should exhibit the following three properties:

Unambiguity

There should not be any ambiguity about what a system to be developed should do. For example, consider the AI-Based Hiring Bias Detector. A requirement states that the system should "fairly evaluate candidates." What does "fairly" mean? It could mean removing only gender bias to one stakeholder, but removing gender, age, ethnicity, and university-origin bias to another. There's an ambiguity. The requirement must explicitly define which bias categories are suppressed.

Consistency

To illustrate this, consider the bias threshold configuration. Suppose one stakeholder says that a candidate should be flagged if the bias confidence score exceeds 0.7, while another stakeholder insists the threshold should be 0.5. Thus, there is an inconsistency between the two end users regarding what they consider an acceptable bias leakage level.

Completeness

A particular requirement for a system should specify what the system should do and also what it should not. For example, consider the AI screening module. If a candidate's resume contains demographic markers (name, age, gender), the system should automatically redact those markers before scoring — and it should not allow any evaluator to view the original unredacted resume during the screening phase.

1.3 Categorization of Requirements

Based on the target audience or subject matter, requirements can be classified into different types:

  • User requirements: Written in natural language so that both customers and developers can verify their requirements have been correctly identified.
  • System requirements: Written involving technical terms and/or specifications, meant for the development or testing teams.

Requirements can also be classified into two groups based on what they describe:

  • Functional requirements (FRs): Describe the functionality of a system — how a system should react to a particular set of inputs and what should be the corresponding output.
  • Non-functional requirements (NFRs): Not directly related to what functionalities are expected from the system. However, NFRs could typically define how the system should behave under certain situations.

Non-functional requirements could be further classified into:

  • Product requirements: e.g., the web application should use HTML5 and responsive CSS
  • Performance requirements: e.g., the system should handle concurrent screening of 100 resumes
  • Organizational requirements: e.g., the development process should follow Agile methodology

1.4 Case Study: AI-Based Hiring Bias Detector (EquiHire AI)

Problem Statement

Organizations across industries face significant challenges in ensuring fair and unbiased hiring practices. Traditional resume screening processes are prone to unconscious human biases related to a candidate's name, gender, age, ethnicity, university origin, and other demographic identifiers. These biases lead to unfair rejection of qualified candidates and reduce workplace diversity.

The AI-Based Hiring Bias Detector (EquiHire AI) has been proposed to address this problem. The system enables job-seeking candidates to register, upload their resumes, and undergo an AI-powered screening process where all demographic identifiers are automatically stripped before evaluation. The AI evaluates candidates purely on the basis of their skills, experience, and qualifications.

Additionally, the system conducts an online aptitude test for registered candidates. The AI scores the aptitude test responses and generates an objective performance report. Based on the combined resume screening score and aptitude test score, the system produces a bias-free shortlist of candidates ranked by merit.

Candidates can view their screening status, aptitude test scores, and shortlisting results through their personal dashboard. The system provides explainable AI audit logs that justify each ranking decision, ensuring transparency and accountability.

An administrator has complete control over the system — they can manage job postings, configure bias detection parameters, view audit reports, and manage user accounts. The system must be accessible as a web application and should ensure that no confidential information (e.g., passwords) is stored in plain text.

1.5 Identification of Functional Requirements

FR-01: New User Registration

Any job-seeking candidate who wishes to use the AI-Based Hiring Bias Detector must register with the system. During registration, the candidate provides: Full Name, Email Address, Mobile Number, Age, and Password (with confirmation). On successful registration, the candidate receives a unique User ID. The system stores age and mobile number in encrypted form, and these details are cloaked (hidden) from any evaluator or screening algorithm to prevent bias.

FR-02: User Login

A registered candidate can log in by providing their email address and password. After successful login, the candidate's personal dashboard is displayed, from where they can access: upload resume, take aptitude test, view screening results, and view shortlist status. If incorrect credentials are provided three consecutive times, the account is temporarily locked for 30 minutes. The user is prompted with a "Forgot Password?" option that sends a password reset link to their registered email address.

FR-03: Resume Upload

A registered and logged-in candidate can upload their resume in supported formats (PDF, DOCX). The system parses the resume to extract: technical skills and proficiencies, work experience duration and roles, educational qualifications, and certifications. The system automatically identifies and redacts demographic identifiers such as candidate name, gender indicators, age, photo, university name, and geographic location before the resume is processed by the AI screening engine.

FR-04: AI-Powered Resume Screening

Once a resume is uploaded and anonymized, the AI screening engine evaluates the candidate based on: skill match percentage against the job requirements, relevance of work experience, depth of technical competencies, and quality of certifications. The system generates a Resume Screening Score (0–100%) for each candidate. The scoring algorithm does not have access to any demographic data. An explainable AI audit log is generated for each score, documenting the factors that contributed to the ranking.

FR-05: Online Aptitude Test

The system conducts an online aptitude test for registered candidates. The test includes: logical reasoning questions, quantitative aptitude questions, verbal ability questions, and domain-specific technical questions (based on the job role). The test is time-bound (e.g., 60 minutes for 50 questions). The AI scores the test automatically and generates an Aptitude Test Score (0–100%). Questions are randomized for each candidate to prevent cheating. Once submitted, the test cannot be retaken for the same job posting.

FR-06: Bias Detection & Reporting

The system continuously monitors the screening pipeline for bias leakage. If any demographic pattern is detected in the scoring distribution (e.g., candidates from a particular age group consistently scoring lower), the system flags it as a bias alert and generates a detailed bias detection report. The report includes: category of bias detected, confidence level, number of affected candidates, and recommended corrective actions.

FR-07: Candidate Shortlisting

Based on the combined Resume Screening Score and Aptitude Test Score, the system generates a bias-free shortlist of candidates. The shortlisting algorithm assigns configurable weightage (default: 60% resume, 40% aptitude), ranks candidates in descending order of combined score, and allows the administrator to set a minimum threshold score. Shortlisted candidates are notified via email.

FR-08: Candidate Dashboard

Each registered candidate has access to a personal dashboard that displays: profile information (with cloaked sensitive fields), resume upload status and screening progress, aptitude test availability and scores, shortlisting status for each applied job posting, and explainable AI feedback on their screening.

FR-09: Administrator Panel

The administrator has elevated privileges to: create, edit, and delete job postings; configure bias detection parameters and thresholds; view system-wide bias audit reports; manage user accounts; set aptitude test question banks and configure test parameters; and export shortlists and screening reports.

FR-10: Search & Browse Jobs

Any visitor (registered or unregistered) can browse and search available job postings by job title, required skills, or experience level. However, applying for a job is restricted to registered and logged-in candidates only.

1.7 Identification of Non-Functional Requirements

Performance Requirements

  • The system should remain accessible 24×7 with a minimum uptime of 99.5%
  • At least 100 candidates should be able to access the system simultaneously
  • The AI screening engine should process a single resume within 10 seconds
  • The aptitude test interface should have a response latency of less than 2 seconds

Security Requirements

  • All passwords must be stored as salted hashes (bcrypt or equivalent) — never in plain text
  • Candidate demographic data (age, mobile number) must be encrypted at rest using AES-256
  • All data transmission must use HTTPS (TLS 1.2 or higher)
  • Session tokens must expire after 30 minutes of inactivity
  • The bias detection audit logs must be tamper-proof and append-only

Software Quality Attributes

  • Reliability: The AI scoring algorithm must produce consistent results for identical inputs
  • Usability: Candidates should be able to complete registration in under 3 minutes
  • Maintainability: Modular architecture allowing individual component updates
  • Scalability: Horizontal scaling to handle increasing candidate volumes

Design Constraints

  • Responsive web application compatible with Firefox, Chrome, Edge, and Safari
  • Front-end must use HTML5, CSS3, and JavaScript
  • AI/ML models must provide explainable outputs (no black-box decisions)
  • System must comply with data protection principles (data minimization, purpose limitation)

Practical 2: Identifying Domain Classes from the Problem Statement

Objectives

  • Understand the concept of domain classes
  • Identify a list of potential domain classes from a given problem statement

2.1 Domain Class

In Object Oriented paradigm, the Domain Object Model has become a subject of interest for its excellent problem comprehending capabilities towards the goal of designing a good software system. Domain Model, as a conceptual model, gives proper understanding of the problem description through its highly effective component — the Domain Classes.

Domain classes are the abstraction of key entities, concepts, or ideas presented in the problem statement. Domain classes are used for representing business activities during the analysis phase.

2.2 Techniques for Identification of Classes

Grammatical Approach Using Nouns

This object identification technique was proposed by Russell J. Abbott, and Grady Booch made the technique popular. This technique involves grammatical analysis of the problem statement to identify a list of potential classes. The logical steps are:

  1. Obtain the user requirements (problem statement) as a simple, descriptive English text
  2. Identify and mark the nouns, pronouns, and noun phrases from the problem statement
  3. List of potential classes is obtained based on the category of the nouns

Advantages: This is one of the simplest approaches that could be easily understood and applied by a larger section of the user base.

Disadvantages: The problem statement may not always help towards correct identification of a class. At times it could give us redundant classes, or the identified class may actually point to an aggregate of classes.

Step 5: Generalization Hierarchy

Among the identified domain classes, Candidate and Administrator share common characteristics — both have a name, email address, and password; both can log in to the system. Therefore, a generalized superclass User can be defined:

User (Superclass)
├── Candidate (Subclass) — can upload resume, take test, view scores
└── Administrator (Subclass) — can manage jobs, questions, users, reports

This generalization follows the ISA relationship in object-oriented modeling.

3.1 Entity Relationship Model

Entity-Relationship model is used to represent a logical design of a database to be created. In the ER model, real-world objects (or concepts) are abstracted as entities, and different possible associations among them are modeled as relationships.

For example, Candidate and Aptitude Test are two entities. Candidates take aptitude tests. So, these two entities are associated with the relationship "Takes".

3.4 Design Considerations

  1. ISA Relationship: Both Candidate and Administrator share common attributes (name, email, password). A generalized User superclass can be introduced, with Candidate and Administrator as specialized subclasses.
  2. Weak Entity: The Aptitude Score entity is existentially dependent on Aptitude Test — it cannot exist without a corresponding test record. This makes it a weak entity.
  3. Derived Attributes: The combined_score in the Shortlist entity is a derived attribute, calculated from resume_score and aptitude_score using configurable weightage.
  4. Data Integrity: The ER model ensures that demographic attributes (age, mobile number) stored in the Candidate entity are never referenced by the Screening Result entity, maintaining the bias-free guarantee at the database schema level.

3.5 Normalization Notes

The baseline ER model prepared above should be revised by considering the business model to ensure all necessary information can be captured. Once finalized, the next logical step would be to:

  1. Create table structures for each identified entity set
  2. Define foreign key constraints for all relationships
  3. Normalize the relations to Third Normal Form (3NF) to eliminate redundancy
  4. Create indexes on frequently queried columns (e.g., candidate_id, job_id, email)
